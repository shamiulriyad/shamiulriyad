20Experimental Design

Eight experiments, A–H, test the research questions. All are designed so that they can be run, and so that a negative outcome is informative. No results are reported in this dossier; none have been produced. This section, together with Sections 21–22, forms the experimental protocol (Artifact 7; also in artifacts/07_experimental_protocol.md).

20.1 General protocol

  • Repetitions: every few-shot setting is run with 5 independent random draws of the reference set (fixed, logged seeds). Report mean ± standard deviation and 95% bootstrap confidence intervals over test images.
  • Statistics: paired comparisons between methods use the same reference draws; significance with a Wilcoxon signed-rank test across categories or draws, Holm-corrected for multiple comparisons (as in [[abbas]]).
  • Thresholds and hyper-parameters (τ, window size, coreset ratio, q) are tuned on validation data only, then frozen before testing.
  • Reporting: every table states the data tier (T0–T4); synthetic results are never merged with real-data results.

Partner data (T4)Split by lot and wafer; never place dies of one wafer in both tuning and test; keep the acquisition date order (train on earlier, test on later) to mimic deployment.
Feedback experimentsThree disjoint pools: feedback stream (dies whose review decisions are fed back), held-out evaluation (never fed back) and canary set (fixed normals + known defects to monitor drift).

20.4 Experiment G in more detail

Because the risk of fooling ourselves is highest here, the protocol is spelled out. (1) Start from memory M0 built from K references. (2) Process the feedback stream in batches of b dies; for each flagged or sampled die, generate the "engineer decision" from ground truth, then corrupt a controlled fraction of decisions (label flips, shifted locations, defect called normal). (3) Apply the update arm. (4) After each batch, evaluate on the held-out set and the canary set, never on dies from the stream. (5) Report learning curves, final gain, worst-case dip, and how often rollback fired. A useful negative control is "update with random normal patches": if it helps as much as the feedback, the gain comes from simply having more memory, not from the feedback.
